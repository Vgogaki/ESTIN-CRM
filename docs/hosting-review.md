# Hosting a review copy for the co-founder

Purpose: let the other co-founder open the system in a browser and review the
work, without it living only on the founder's laptop. This is a **review copy,
not production**. A real launch still needs the contractor's Foundation Setup
(`deployment.md`) and the independent security review (build plan Part 1).

## What the review copy is (and isn't)

| | |
|---|---|
| Where | Render, **Frankfurt (EU)**, one always-on web service plus one private database (`render.yaml`) |
| Data | **Fake demo data only** (8 traders, 3 products, a competition, an affiliate...). Nothing from the founder's laptop is copied: not her trader record, not any KYC document, not any password or key |
| Emails | Never delivered. They are recorded and readable at Back office > **Email** |
| Who can reach it | Only people with the **gate password**, and then only people with an admin login |
| Files | Uploaded KYC/support files are encrypted but kept on temporary storage and disappear when the service restarts |
| Cost | Roughly $13/month (small web service + small database). **Check current Render pricing**; delete the service when the review ends |

## Security layers

1. **Gate password in front of the whole site.** Before anyone sees even a login page, the browser asks for a username and password. Strangers, scanners and bots get nothing. If the password were ever missing, the site refuses everything (it does not open up).
2. **The app's own admin login behind it.** Separate accounts for the founder and co-founder, with lockout after repeated wrong passwords or wrong codes. **Two-factor sign-in** is available: each admin turns it on at Back office > Your account > Two-factor (authenticator app plus 10 one-time recovery codes). Do this on first sign-in; a sidebar reminder shows until it's on.
3. **Fresh secrets, generated by Render.** The encryption key, session secret, API key and all three passwords are created on the host and shown only on its Environment page. They never pass through chat, email or the code repository.
4. **Database not reachable from the internet** (`ipAllowList: []`); only the app can talk to it.
5. **HTTPS only**, plus browser security headers; the site tells search engines not to index it.
6. **Demo-seed safety rail.** The demo data loader refuses to run if any real (non-demo) person exists in the database, so it can never overwrite or mix with real data.
7. **Private code repository**, invite-only.

## Steps

### Done by Claude (in this repo)
- Password gate, security headers, health check, demo data, hosted-copy admin accounts, container changes, `render.yaml`. All tested against the built container image.

### Done by you (needs your accounts and payment; nobody else can do these)
1. **Create a private GitHub repository** (empty: no README, no .gitignore). Add your co-founder as a collaborator with **Read** access if they should also see the code.
2. **Tell Claude the repository address.** Claude connects the project to it and prepares the push. Pushing publishes the code, so you confirm it first; you may need to sign in to GitHub once in the window that opens.
3. **Create a Render account.** Add a payment card yourself.
4. In Render: **New > Blueprint**, pick the repository. Render reads `render.yaml` and shows what it will create (one web service, one database, both in Frankfurt). It asks for one value: **`SEED_COFOUNDER_EMAIL`**, your co-founder's email. Click **Apply**.
5. Wait for the first deploy (about 10-15 minutes). Open the web service > **Environment** and copy:
   - `REVIEW_GATE_PASSWORD` (gate username is `reviewer`)
   - `SEED_FOUNDER_PASSWORD` (your admin login: valentina-gogaki@hotmail.com)
   - `SEED_COFOUNDER_PASSWORD` (their admin login: the email you entered)
6. **Send the co-founder the address, and the passwords through a different channel** (a password manager share, or a call). Not all in one email.
7. Co-founder opens the address, enters the gate username and password, then goes to `/admin/login`.

### What the reviewer should know
- Everything is fake data: traders are `@demo.estin.test`. Pending tasks shows ready-made cases (a pass review, a KYC check, a funded trader without KYC, a breached trader, a support thread).
- Emails are not sent; read them at Back office > Email.
- Back office > **Test tools** (granting accounts) exists for demos and must not exist in production.
- Things that need a vendor or decision are not wired up and are listed in `deferred-items.md` (trading platform, payments, payout rails, email provider...). The review shows the system as built, not a launched product.

### When the review ends
Delete the web service **and** the database in Render, and rotate nothing else: none of these secrets exist anywhere else. Remove the co-founder from the repository if you wish.

## Known limits (honest list)
- **Not security-reviewed.** The gate and headers reduce exposure; they do not replace the independent review before real customer data.
- **Admin two-factor is available but not mandatory,** so an admin who ignores the reminder is protected by the password (and the gate) only. Before real data, make it compulsory for back-office staff. Also: the authenticator secret is stored unencrypted in the database (same for traders), and a code can be reused within its 30-second window (no replay protection).
- **No Content-Security-Policy yet** (needs careful testing against the Next.js build).
- **Client IP is taken from the first `X-Forwarded-For` value.** Behind a host's proxy that value can be influenced by a visitor, which would weaken the IP shown in the audit log and the IP-based checks. Production hosting must trust only the platform's own proxy address. (Contractor item.)
- **The build downloads fonts from Google at build time.** A one-off failure of that download fails a deploy; redeploying fixes it. Bundling the fonts into the repository would remove the dependency.
- The image is large (~1.7 GB) because the full dependency set ships in it (documented in the Dockerfile).
- `KYC_ENCRYPTION_KEY` must decode to exactly 32 bytes; Render's generated value is expected to, but confirm by uploading one test KYC file after the first deploy (the app only checks the key when it is first used).
